# AGENTS.md — Onn 4K launcher (read this first, do not re-discover)

Keep this file static (no dates or run logs) so it stays a cacheable prompt prefix. Put per-session notes in chat, not here.

## 0. Rules
1. Connect to the box FIRST (section 1). Never build before `adb devices` shows it.
2. This repo IS the installed launcher's source. Diff and edit it; never rewrite from scratch or re-scaffold.
3. Apply file changes directly and test on the device yourself. Do not ask the user to approve or test.
4. Be concise. Don't re-explain Onn 4K or ADB basics.
5. Don't touch `android/` unless a native feature changes. The shell is stable.

## 1. Connect (always first)
- Device: Onn 4K Plus, `10.0.0.79:5555` (Wi-Fi ADB).
- `adb connect 10.0.0.79:5555`, then `adb devices` must show `device`. If offline: `adb kill-server; adb connect 10.0.0.79:5555`. If it still fails, tell the user to enable network debugging on the box.
- Use `adb -s 10.0.0.79:5555 ...` for every command.

## 2. Architecture
- Web UI: Next.js 16 static export (`output:'export'` in `next.config.mjs`; keep it, `standalone` breaks the build) → `out/`.
- Shell: Kotlin WebView app `com.hxxdy.launcher` in `android/`. Gradle `copyWebAssets` copies `out/` into the APK assets. The shell serves them at `https://launcher.local/` and exposes `window.LauncherBridge`.
- Hybrid playback: `MainActivity` hosts `FrameLayout { NativeVideoSurface; WebView }` with a transparent window and a transparent WebView. The live wallpaper is decoded by a `MediaPlayer` onto a `SurfaceView` **behind** the page (`NativeVideoSurface.kt`), driven from `hero-backdrop.tsx` through `playLiveWallpaper` / `pauseLiveWallpaper` / `stopLiveWallpaper`. While it plays, `html[data-native-video='true']` makes html/body/main see-through (globals.css) so the surface shows; every other state is opaque, so nothing else changes. The DOM `<video>` stays as the browser/old-shell fallback and is not rendered when the native path is active. Verified better on the box than the DOM decoder: ~1 % idle jank instead of ~2 %, and Continue focus movement 36 % / 50th 36 ms instead of 43 % / 44 ms, with the launcher PSS ~44 MB lower.
- Artwork pipeline: `LauncherWebViewClient` intercepts `image.tmdb.org` / `play-lh.googleusercontent.com` plus the `content://` Watch Next art, decodes them natively (≤500 px posters, ≤1280 px backdrops), and serves them from a 24 MB `LruCache` + a 200 MB disk LRU in `cacheDir/artwork` (`Cache-Control` 7 days). Any failure returns `null` so Chromium loads the image itself - never break an image to save memory.
- Cached shell payloads: `LauncherBridge` memoizes the serialized `getApps` / `getWatchNext` / `getYouTubeHistory` JSON and only re-reads `PackageManager` / TvProvider when `MainActivity` invalidates it — `invalidateWatchNext()` from the Watch Next `ContentObserver`, `invalidateAllCache()` on a package broadcast or `onResume`, both before dispatching `launcher:refresh`. Resume drops the cache on purpose: provider data changes while the observer is unregistered.
- Icon pipeline: `https://launcher.local/__icon/<pkg>` (16:9 banner) and `/__app_icon/<pkg>` (96 px tile) are drawn from `PackageManager` once and kept in the same 24 MB `LruCache`, served `Cache-Control: no-store` so the WebView cannot pin a pre-update drawable; `MainActivity` calls `invalidateIcons()` on every package broadcast. Never query `PackageManager` or re-encode a bitmap per scroll.
- Renderer priority: `MainActivity` sets `setRendererPriorityPolicy(RENDERER_PRIORITY_IMPORTANT, false)` so Android 14 cannot drop the WebView renderer/compositor to background priority when a service wakes. Hardware acceleration stays on; the transparent `SurfaceView` composite is unaffected.
- Row caps: `tv-launcher.tsx` slices the Continue Watching shelf to `CONTINUE_LIMIT` (10) and the Your Taste deck to `TASTE_LIMIT` (6), both at the data layer so the `1 / 10` and `1 / 6` captions count exactly what is mounted; the taste preloader then decodes six picks instead of the whole history (2 GB box).
- Logo luminance: `lib/logo-luminance.ts` owns ONE verdict per wordmark URL (in memory + `localStorage` `launcher.logo.luminance.v2`, 300 URLs, oldest dropped; the `v1` key is deleted on first read because that file judged brightness only). ONLY a monochrome black wordmark is flattened to crisp white with `filter: brightness(0) invert(1)`: at least 90 % of its opaque ink (`alpha > 32`) must be near-black (`R,G,B < 45`) and no pixel may exceed `max(R,G,B) - min(R,G,B) < 28`. One coloured pixel settles it as colour and the artwork is left untouched (Nocturne turns white, Spider-Man never does). A tainted `getImageData` records nothing - the logo stays as authored rather than guessed. `hero-info.tsx` probes the `<img>` it already loaded; `title-lockup.tsx` (Continue Watching and Your Taste cards) probes an offscreen 192 px `crossOrigin` image, so mounting a card never does a synchronous GPU->CPU readback and no URL is probed twice. `LauncherWebViewClient` answers TMDB *and* metahub (`images.metahub.space`, whose 307 it follows) images with `Access-Control-Allow-Origin: *` - without it every hero probe taints and no logo can be judged. Never probe a URL that already has a verdict, never probe the same URL twice, and never probe inside a spring/animation frame - the hook fires on mount, before the card is moving.
- Shell files (`android/app/src/main/java/com/hxxdy/launcher/`):
  - `MainActivity.kt`: Back/Menu are sent as synthetic `Escape`/`ContextMenu` keydowns; fires `launcher:refresh` and `launcher:home` window events; owns the payload/icon invalidation and the renderer priority.
  - `LauncherBridge.kt`: the native bridge, with the payload caches above.
  - `LauncherWebViewClient.kt`: artwork pipeline, plus the cached app icons at `https://launcher.local/__icon/<pkg>` (16:9 banners) and `/__app_icon/<pkg>` (square tiles).

## 3. Native contract (UI code MUST honor)
All real data comes through `lib/native-bridge.ts`: `isNative, loadApps, loadContinueWatching, heroFromContinue, hasWatchNextAccess, requestWatchNextAccess, getNetwork, launchApp, launchIntent, openSystem, openAppInfo`.
- Apps are `{pkg, label, icon, service?}`. Continue items and slides have NO guaranteed `service`; it is optional everywhere. Never index `services[x]` without a guard. That exact crash broke the launcher before.
- Static demo data in `lib/launcher-data.ts` is only the browser (non-native) fallback.
- Never read localStorage or the bridge during first render. `tv-launcher.tsx` renders a blank `<main>` until a client `useEffect` sets `ready` (prevents React hydration error #418).
- Hero slides = trending movies and series only (`lib/nuvio-featured.ts`, Cinemeta catalog, cached 6 h in localStorage), shown only if `com.nuvio.tv` is installed. Do not put Continue Watching in the hero.
- Hero action text: "Playing" for trending (`logoIsAlpha`), "Resuming" otherwise.
- Nuvio deep link: `intent://tmdb/{type}/{id}#Intent;scheme=nuvio;...;package=com.nuvio.tv;...;end`.

## 4. File map (`components/tv/`)
- `tv-launcher.tsx`: controller. Zones nav/hero/continue/apps, key handling, long-press (500 ms on Enter over an app tile enters Organize & Move; App Info is an explicit button in the organize row), Enter activates on keyup, `launcher:home` resets, stack translate-Y scrolling. The launch overlay is shown first and the target app starts 300 ms later; the overlay clears itself after 2.2 s, and is also dropped explicitly on refresh, Home, resume and `visibilitychange` (WebView timers freeze behind another app, so a self-clearing overlay would otherwise still be on screen when the launcher is revealed).
- `theme-modal.tsx`, `theme-creator.tsx`: self-contained with their own key handling. `tv-launcher` key handling must return early while they are open.
- `top-header.tsx` takes `items` (native nav labels). `apps-row.tsx` renders `app.icon` as `<img>`. `launch-overlay.tsx` `LaunchState = {key, name, service?, icon?, action}`.
- `profile-modal.tsx`: the full-screen Profile menu, opened from the nav profile pill; wired in `tv-launcher` with `themes` and `onUpdateColor`.
  - Spatial zones `header` / `cards` / `actions` / `colors`; Back steps back one zone before closing.
  - The card strip is the reference's single `<ul>` (`justify-center`, `overflow-x-auto`). With all six profiles its centred overflow can push the first card past the left edge, where `scrollLeft` cannot reach it: that is the reference's own behaviour, kept for parity, so do not reintroduce a scroller wrapper unless the user asks.
  - Rename and naming a new profile open `TvKeyboard` in text mode; avatar swatches persist through `onUpdateColor`.
- `lib/profiles.ts`: profile state (`MAX_PROFILES = 6`, `PROFILE_COLORS`, localStorage keys `launcher.profiles` / `launcher.activeProfile`), loaded and saved only by `tv-launcher`.
- `your-taste-row.tsx`: the "Your Taste" deck (concave 3D poster carousel, dot indicators, focused-title pedestal). Items come from `lib/taste.ts`; `service` is optional and the row labels `Stream` when a pick has none.
- `lib/taste.ts`: builds the deck from the Watch Next titles the shell exposes (genre seeds, series detected from `S5 · E10` details) scored against the Cinemeta popularity catalogs Nuvio browses, cached 3 h in `launcher.taste.v1`, deep-linking each pick into Nuvio. Falls back to the bundled `tasteItems` when the network or history yields nothing.
- `continue-watching-row.tsx`: the metadata cluster captions `item.detail` as `Episode` (`S2 · E4`, an episode title) and as `Category` when the detail is `Film`/`Movie` - a film is not an episode.
- `lib/logo-luminance.ts`: the shared dark-wordmark verdict (memory + `localStorage`), used by `hero-info.tsx`'s `TitleLogo` and by `title-lockup.tsx`.
- `lib/layout.ts`: `SHELF_ANCHOR`, the fraction of the viewport each shelf's top edge rests at when focused. The stack scroll and the hero's reserved bottom band both read it, so the hero can never sit under the next shelf's landing position. Each homepage section is one `dvh` tall (`hero-info.tsx` is `h-dvh` with a shrinkable band as its last child).
- `lib/utils.ts`: `cn`, `signedOffset` (circular index distance). `lib/navigation-sounds.ts`: remote-key click sounds. `title-lockup.tsx`: wordmark/fitted-text renderer shared by the shelves.
- `settings-modal.tsx`: the Settings overlay (tabs Display & Video / Launcher / Audio / Apps / Network / System, D-pad zones tabs↔content, content focus enumerates `button:not(:disabled)` so new buttons join the remote order automatically). The Display tab ends with two pills side by side: **Open Android Display Settings** (`openSystem('display')`) and **Amlogic AI Picture (AI-SR)** (`openSystem('amlogic')`). The Amlogic pill is passed only when `data.native`, and `tv-launcher` toasts "Could not open Amlogic picture settings" when the bridge returns false — keep that fallback, the shell returns false rather than throwing.
- `tv-keyboard.tsx`: the on-screen keyboard for both search bars and text entry, `mode: 'search' | 'text'` (default `search`). Mounted only while open; `apps-menu-modal` opens it only when the search bar is activated, never on focus or D-pad navigation. It uses the original full-size key metrics (780 px panel, `clamp(36px,4.4vh,46px)` keys), and Up from its top row is a no-op, as in the reference (Escape/Back and the close or Done control close it). In My Apps it searches the live Play catalog as you type, Done closes it and focuses the first result, and `Open Play` launches `market://search`. Profile renaming uses text mode.

## 5. Porting a new design (fast path)
When the user drops new UI code (e.g. `hxxdy (2)`, AI Studio exports):
1. Connect (section 1). Don't build yet.
2. Diff the drop against this repo's `components/tv/` and `lib/`. Port only visual/layout changes into the existing files.
3. Keep `native-bridge.ts`, `nuvio-featured.ts`, `profiles.ts`, the `tv-launcher.tsx` logic, and `next.config.mjs`. Never overwrite them with the drop's versions, and keep the optional-`service` types in `launcher-data.ts`.
4. Check every new component against section 3 (optional `service`, no static-data assumptions, no render-time storage/bridge reads) and section 7.
5. `npx tsc --noEmit` must be clean. The build has `ignoreBuildErrors`, so run it yourself.
6. Deploy and verify (section 6).

## 7. Performance rules (Cortex-A55)
No `backdrop-blur` (a rule in `globals.css` also neutralizes it), no `mix-blend-mode`, mount only current/previous/next hero slides, use `offsetLeft` rather than `getBoundingClientRect`, no smooth-scroll inside modals, keep transitions short (500 ms or less).
- Raster budget (2 GB box): `will-change-transform` is on the ±1 cards of the shelf that CURRENTLY HAS FOCUS only (`rowFocused && abs <= 1` in both carousels); the ±2/±3 cards are never promoted, so they stop pinning seven layers and their rasters. `FlowFill` takes `active` and sets `animation-play-state: paused` when it is false (`active={rowFocused}` in both carousels, `active={visible && !paused}` in the hero), which writes `data-tv-flow-active='true'` on the track: only that attribute turns the animation on, so an unfocused shelf keeps a static gradient with `will-change: auto` and leaves the compositor nothing to redraw. `.tv-halo-glow` carries NO `filter: blur()`: the spinning conic child is feathered by one static radial `mask-image` ramp and spills `4 x --tv-halo-blur`, so a frame composites the rotation instead of re-filtering the card silhouette - the blur was the single most expensive thing in the UI (~40 % -> ~17 % janky on Continue when disabled), and with it gone Your Taste measures 1.6 % janky / 50th 27 ms / 90th 31 ms on the 12-press shape. Do not reintroduce the filter. Over the live video (`nativeVideo && wallpaperActive`) the three wallpaper scrim passes are ONE element - normal-blend backgrounds composite identically - so two fewer full-screen surfaces are blended per frame; the immersive stage only carries `will-change-transform` while it is on screen. Continue Watching asks for `w500` art on every non-centre card (the shell caps `/w500/` at 500 px, a backdrop at 1280), its progress fill has NO width transition (it re-animated inside the springing card), and its arc geometry is ONE map for both states - `revealed` must never change `xVw` again, or entering the shelf slides all seven cards sideways on the focus spring.
- Never animate a gradient angle or a filter radius. `.tv-conic-border` is a STATIC diagonal gradient (`linear-gradient(135deg, --tv-accent, --tv-accent-2, --tv-accent)`) on focused cards, app tiles and every circular Play button/pill: no pseudo-element, no animation, not on any other element. `.tv-halo-glow` is the only orbiting layer - the Gemini-style aura, a fixed blur around a conic child spun with `transform` on `@keyframes tv-ring-spin` / `--tv-ring-duration` (4.2 s). The bloom's feather is **8 px** (`--tv-halo-blur: 8px`; the reference's 13 px blur) and it exists **only on the card/tile perimeter**: the centre Play circles keep their static ring but carry no halo of their own, because a second blurred layer over the same card was a second full Gaussian pass per frame for a glow the card already gives. Animating `--tv-grad-angle` repainted the whole layer and re-blurred the halo every frame (that was the shelf stutter). The rotating gradient inside the blurred halo does re-blur, but only for the one focused halo: measured ~16 % janky frames idle vs 0.5 % with the sweep held still. Never put a rotating layer inside a blurred *shelf*, and never give the ring its rotation back: a spinning layer behind every focused card cost a full-surface raster per frame and bought nothing the static diagonal does not. The ring is on every focused card/tile (both carousels, app tiles, All Apps) and on every Play control (Continue and Your Taste centre Play circles, hero Play pill, launch-overlay icon, theme-creator mini pill), so cards and pills always share the same treatment.
- `.tv-conic-border` renders BEHIND the opaque surface it outlines and overhangs it by 1.5px. It is a SIBLING of that surface, placed inside the card container (button/tile wrapper) so it tracks the card's scale, tilt and spring in lockstep, but never a child of an `overflow-hidden` surface, which would clip the overhang away. Call sites pass that surface's radius inline. Never go back to a mask ring: **no** mask form clips on this WebView. The reference's `mask` + `mask-composite: exclude` pair leaves both layers opaque and floods the button, and so does the legacy `-webkit-mask` + `-webkit-mask-composite: xor` pair (both rebuilt and photographed: the focused Continue card and the hero Play pill turned into a flat conic wash). That is why the band is produced geometrically, by the wrapper's 1.5px overhang past an opaque surface. Consequence: the ring can only be a sibling BEHIND the surface it outlines. Putting it inside the pill/surface (as the reference does) paints the whole gradient across the button — that is the one change that must never be made. Because the ring is static it carries no oversized spinning child and needs no `overflow` clip: it is only the 1.5px gradient band left visible behind the opaque surface. Do not reintroduce the pseudo-element or the clip.
- Carousel motion is `motion/react` springs (Continue Watching stiffness 205, Your Taste 215, both damping 25 / mass 0.92) on `transform`, plus `width`/`height` for Continue Watching. This is the design and was restored deliberately for visual parity: main-thread-framed springs re-raster every perspective card each frame, so this shelf is the most expensive part of the UI (measured ~46 % janky frames while moving Continue focus on the shipped build; see the reference points below). Do not "fix" it by swapping the springs for `linear()` CSS transitions or by moving the halo/ring to a stage layer: both change the look and the user rejected them. Optimize inside that constraint (keep `height` numeric with static `minHeight`/`maxHeight` so the spring interpolates a single unit, cached logo luminance probes, deferred bridge refresh after paint).
- Both carousels use the SAME 5-card visible arc: `abs > 3` returns null, so 7 cards are mounted - centre, ±1, ±2 peeking in from the screen edges and ±3 off screen - and 5 of them are on screen at rest. Continue Watching springs on 205, Your Taste on 215. The outer pair rides the same spring at `opacity: 0`, so cards glide in and out instead of popping in at ±2 — do not cut the mount range back to ±1/±2; that pop and the missing edge lockups are the regression the user reported. Focus halos and rings live INSIDE the card container, around the card surface, never in a static stage layer, so every border, halo and highlight moves, scales and tilts with its card on every frame.
- A blurred, spinning halo is a child of a card that the spring scales, so it re-rasterizes its blur while the row animates. That cost is part of the approved design. Never add a second such layer per card, and never put one on a shelf that is not focused.
- There is no `settling` flag, no `.tv-halo-fake` and no `[data-settling]` rules any more: every focused card keeps its real 13 px bloom with the sweep running straight through the spring. Those were the workaround for the rotating ring and the resizing card. If jank has to come down again this is the first place to look, but re-adding the swap changes the look, so measure it as a win and get sign-off first.
- The Continue arc no longer resizes anything: every card is ONE fixed `38vw x 19.4vw` layout box (`minHeight: 174px`, `maxHeight: 320px`) whose 205 spring animates `scaleX`/`scaleY` (centre `1`/`1`, side `20/38` x `17.6/19.4`). Inside, the role box is counter-scaled by `1/scaleX`, `1/scaleY` so text, logos, the Play control and the progress bar keep their authored size, and `xCorrection`/`yCorrection` cancel the hinge origin (`CARD_BOX_*` / `SIDE_SCALE_*` in `continue-watching-row.tsx`) so every card lands exactly where the width/height layout put it - a step is a transform, not a layout. Cost: mid-flight the card scales anisotropically, so artwork is briefly off-aspect; that is what buys the missing layout pass. Measured: layout 0.3 ms and raster ~34 ms per frame, so frame time is unchanged (17.3 % janky / 50th 29 ms / 90th 97 ms on the 12-press shape); the gain is one layout per step instead of 60/s, plus memory. Do not expect a frame-rate jump from geometry alone - the floor is the blur/video composite. Earlier measurements on the old build: Continue 37-40 %, Your Taste 14.4 % (same 205/215 spring, same halo, but a fixed card size), My Apps 8.7 % (transforms only). Removing the bloom during the spring entirely changed nothing (37-39 %), and neither a single small cast shadow nor mounting two fewer off-screen cards moved it. So do not spend more effort on filters or shadows for this shelf: it re-lays-out seven cards and re-rasters their artwork at every intermediate width, and that is the cost. Going under ~15 % means replacing the resize (clip a fixed-size artwork layer, or transform-scale the box with counter-scaled content), which changes how side cards frame their artwork mid-slide and needs sign-off first.
- The orbiting bloom is the single most expensive thing in the UI, and it is the bloom, not the springs: disabling only `.tv-halo-glow`'s `filter: blur()` takes Continue Watching focus movement from ~40 % to ~17 % janky frames and idle from ~15 % to 0.5 %, while `framestats` shows traversal 0.3 ms / draw 0.5 ms per frame. The blur must follow the clip (clip then blur), so it can never be composited as "blur once, rotate the result": every frame re-filters the card's whole silhouette (~370 k px at `38vw`). No cut remains in the shipped design: the Continue shelf uses the reference 13 px bloom and no longer parks the sweep during a spring, since both the 8 px reduction and the `[data-settling]` pause went with the rotating ring. Either can come back if the box needs it, but both change the look, so measure and get sign-off first. Ruled out by measurement, do not re-try: a fixed-size spinning ring raster (`--tv-ring-size`, since removed — no change; the square is back to 200 % of the surface width), laying the halo out at half size and scaling it up with a halved blur (Chromium rasters at the final scale, 15.7 %/46 %: no change), `will-change: filter` (no change). The floor: with the blur disabled the same scene measures ~17 % moving and 0.5 % idle, so what remains is the re-filter itself, once per frame, for as long as the box changes.
- Reference points on Continue Watching, `dumpsys gfxinfo` after a fresh start, all single ad-hoc runs of the same shape (12 rapid right presses), so treat differences under ~5 points as noise: the stage-halo build this UI was restored from ~48 % / 46–48 ms; the in-card build with the 8 px bloom and the (since removed) settling window ~34–39 % / 42–48 ms; the shipped static-ring build with the 13 px bloom and no settling window ~46 % janky / 50th 48 ms / 90th 300 ms. That last figure is the expected baseline for the approved design: do not "recover" the old number by shrinking the bloom or re-adding the fake halo unless the user asks. The 4.5 %/21 % figures above come from a different scene, so do not use them as this shelf's target. After the raster trim (8 px bloom, no Play-button halo, promotion limited to the focused ±1, paused flow tracks, w500 side art): ~17-20 % janky, 50th 21-34 ms, 90th 69 ms on the same 12-press shape, with the first pass after an install still paying a ~300 ms tail while the new w500 posters are fetched and cached - measure the second pass, not the first.

## 8. Box state set over ADB (keep it)
- Amlogic picture/AI-SR: `Enable AI SR` is stored ONLY inside Amlogic's own stack (`com.droidlogic.AiPqService` + the vendor `SystemControl` HAL). Toggling it changes NO `settings list global|system|secure` key (full three-namespace diff before/after is identical, and no `pq`/`ai`/`sr` key or system property exists), and it survives a reboot. So there is nothing to write from the launcher: do not add startup code that "enforces" it and do not grant `WRITE_SECURE_SETTINGS` for it. Reach the menu with `openSystem('amlogic')` → `com.droidlogic.tv.settings/.more.MorePrefFragmentActivity` → Picture → AI-PQ/AI-SR (that activity is the ONLY exported vendor entry; there is no Picture activity on this firmware, and the `:settings:show_fragment` extra is ignored).
- Appops: `com.google.android.youtube.tv` has `RUN_IN_BACKGROUND` and `RUN_ANY_IN_BACKGROUND` = `ignore`. `com.hxxdy.launcher` and `com.surfshark.vpnclient.android` must stay `default` (unrestricted) - the launcher needs to resume its wallpaper/watch-next refresh, and the VPN must reconnect in the background.
- Animation scales: `window_animation_scale` 0.5, `transition_animation_scale` 0.5, **`animator_duration_scale` 1.0** (the WebView CSS/`motion` animations are timed against the animator scale; changing it changes the carousel springs' feel).
- Home: `com.hxxdy.launcher/.MainActivity` is the default home. `com.google.android.apps.tv.launcherx` (Google TV Home) is deliberately disabled and must stay disabled; there is no `com.google.android.tvlauncher` package on this Android 14 image.
- Display / 1080p UI rendering: the panel is 3840x2160, HDR10/HLG/DV/Technicolor reported, and the active mode is id 48 at 59.94006 Hz; `dumpsys display` shows `logicalFrame=Rect(0,0 - 1920,1080)` over `physicalFrame=Rect(0,0 - 3840,2160)`. That is `wm size` carrying an intentional `Physical size: 3840x2160` + `Override size: 1920x1080` / `wm density 320`, so Chromium composites the whole UI at 1080p (a quarter of the fill rate) and the display pipeline - Amlogic AI-SR included - upscales it to the 4K panel. Verify with `adb shell wm size` and `adb shell dumpsys display | grep mBaseDisplayInfo`; if the override is ever cleared, every `vw`/`dvh`/`clamp()` still resolves, but at 4x the raster cost and with slightly different `clamp()` pixel caps, so treat it as a rendering change, not a free 4K upgrade.
